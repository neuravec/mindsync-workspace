Prod audit 2026-09-01 (task: verify a user's false "add your next session date" push complaint) surfaced a durable, reusable code fact plus a data-audit-trail gap.

**Durable code fact - `next_session_date` cannot be trusted as "the" next session anywhere in the codebase.** It is only ever consumed as an *anchor* input (biweekly week-parity math, custom-interval math in `compute_next_session_date`/`therapy_schedule_utils.py`) - never as a standalone answer. Every one of the ~10 call sites that read it (`crud.update_therapy_schedule`, `crud.get_therapy_schedule_with_frequency`, `therapy_tracking.get_session_cycle_state`, all 7 `app/services/moments/*_generator.py` files, `notification_service.py`, `prep_card_auto_generate.py`, `weekly_observations.py`) passes it in as `anchor_date=` and separately computes the real answer from `therapy_schedule` (recurring weekly/biweekly JSON entries) or `custom_therapy_sessions` (calendar-picked one-off JSON entries). If a user's schedule data lives ONLY in `next_session_date` with both of the other two columns empty, every eligibility check in the app treats them as having no upcoming session at all - this is a structural gap, not a bug in any single generator. Verified globally (2026-09-01, last 30 days of ADD_THERAPY_DATE recipients): 0 users currently hit this exact "future next_session_date but empty schedule/custom" state, so it is not presently a visible systemic driver, but it remains a live structural trap for anything that only ever writes `next_session_date` without also writing `therapy_schedule`/`custom_therapy_sessions` (the only real write path, `PUT /therapy-schedule`, always requires a `schedule` list and optionally `custom_sessions`, so this can only be reached by a future code path that writes `next_session_date` directly, or by a partial/failed write).

**`user_preferences` has NO `updated_at`/`created_at` column at all** (confirmed live via `information_schema.columns`, not assumed from `models.py`). There is no way to answer "did the user's edit land before or after the system reacted to it" from this table - the second time this exact class of question has hit that wall (see [[project_onboarding_field_save_bug_2026_06_29]] for the first). If this keeps recurring, recommend `backend-api` add an audit timestamp.

**The pre-2026-08-16 ADD_THERAPY_DATE flood (documented in [[project_notification_moments_worker_registration_bug_2026_07_03]]'s sibling post-release-review, and in the generator's own docstring) still dominates any 30-day rolling window as of 2026-09-01** - 24,694 of 24,715 (99.9%) moments in the last 30 days carry `scoring_signals->>'date_status' = NULL` (the pre-fix generator never set this key), reproducing the same 0.21% engagement rate the original review found. Only ~21 moments/13 users in the full 16 days since the fix carry the new `date_status` tag - the 7-day-cooldown + 3-strikes give-up throttle gave up on almost the entire previously-spammed population almost immediately, since most had already accumulated 3+ unengaged sends before the fix shipped. **Practical implication for future audits**: a `created_at > now() - interval 'N days'` filter on ADD_THERAPY_DATE will keep looking "sick" (mass volume, near-zero engagement) for weeks after the actual fix shipped, purely because old rows are still inside the window - check `scoring_signals->>'date_status'` or filter on the actual fix date, don't just trust the aggregate.

**Practical fingerprint for "is this ADD_THERAPY_DATE complaint about the pre-fix bug or a live one":** pull the user's own moment history. Pre-fix rows are daily with zero gaps, `date_status IS NULL`, and the copy is always the "never set" branch ("You haven't set an upcoming therapy session yet..."). If those rows stop abruptly and stay stopped while the user's OTHER moment types (WEEKLY_SUMMARY_READY, THERAPY_RELATIONSHIP_CHECKIN, etc.) keep firing normally, that's the give-up throttle working as intended, not an outage - confirms the account isn't globally suppressed.
