Tester `[e-mail testera A]` (single account, `user_id=<UID-3>`, registered 2026-08-17) hit "already have premium, can't buy" on Android with **zero receipts ever submitted**. Root cause traced in code + confirmed live: `POST /users/subscription` unconditionally calls `_create_initial_subscription(db, user_id, 4, mark_had_trial=False)` (`MindSync/app/api/v1/endpoints/users.py:111-164,402-426`) for every new user (iOS or Android) — sets `user_subscription.subscription_type=PREMIUM, is_active=True, end_date=+4d`, no receipt, no promo, no store transaction. This is intended behavior (operator-confirmed standard free trial), not a data bug by itself.

**The bug:** `user_subscription` (live prod columns: `id, user_id, subscription_type, start_date, end_date, is_active` — verified via `information_schema`, no drift here) has **no source/origin column whatsoever**. `user_subscription_trial.had_trial` looks like it should be the signal but isn't — it's reserved for Apple/Google **in-app-purchase** trial offers (set from `is_trial`/`paymentState==2` during receipt verification), a different concept; the signup grant passes `mark_had_trial=False` and never touches it. Canonical gate `is_user_premium()` (`MindSync/app/api/v1/endpoints/_therapy_helpers.py:28-51`) = `is_active==True AND (end_date IS NULL OR end_date>NOW())` — structurally cannot distinguish trial from paid. Whatever shows "already have premium, can't buy" to the user reads this same undifferentiated `is_active` flag (did not trace into Flutter — flutter-mobile's domain — but ruled out a backend purchase-time rejection: no cross-account/HIGH-001 guard fires, since `find_cross_account_receipt` only runs post-receipt-submission and this user submitted none).

**Scale (2026-08-17, prod-wide):** of 13 users currently `is_active=True` with unexpired `end_date`, **8 have zero VERIFIED receipt** (trial-only premium; 6 of those registered in the last 30 days) vs 5 genuinely paid. So 62% of "premium" users right now are actually unconverted trial grants — this reproduces for every new signup during their first 4 days, not just this tester.

**Why:** determines whether a DB-level UPDATE can safely "fix" this — it can for one user, but the schema gap means it will recur for every new signup until `backend-api`/`flutter-mobile` add a source distinction and fix the purchase-blocking check to allow "convert from active trial."

**How to apply:** if asked again "why does a brand-new user get blocked from buying" — check `user_subscription.is_active` + absence of a `subscription_receipts` row for that `user_id`, not `user_subscription_trial.had_trial` (that column will read False/NULL even during an active signup trial — do not treat it as the trial signal). The minimal narrow unblock for a single affected user: `UPDATE user_subscription SET is_active=false WHERE user_id='<uid>'` — sufficient on its own because `is_user_premium()` is an AND, and this is exactly what the existing hourly `deactivate_expired_subscriptions` job (`MindSync/app/services/subscription_service.py`) will do to that row naturally once `end_date` passes; no need to also backdate `end_date`. Full report + exact SQL (not executed): `db-reports/2026-08-17-tester-premium-block-recon.md`.
