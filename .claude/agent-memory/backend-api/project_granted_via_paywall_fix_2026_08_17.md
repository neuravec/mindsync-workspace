Incident: a tester's NEW Android account, given the standard 4-day free trial at signup, saw "you already have premium" and could not open a real purchase. Root cause is 100% frontend (Flutter): `subscription_screen.dart` (`SubscriptionScreen.build`, ~line 50/71-79) swaps the entire paywall for a no-buy-button `PremiumView` whenever `MainPageCubit.userInfo?.subscriptionIsActive == true`, with zero distinction between a free trial grant, a promo code, and a real verified purchase -- `_create_initial_subscription` (signup trial), promo redemption, and `_activate_user_subscription`/`activate_user_access_until` (real purchases) all write the exact same `is_active=True, subscription_type=PREMIUM` shape to the same `UserSubscription` row. Backend never rejects a purchase for "already premium" anywhere (checked `/subscription_data` and `/one_time_purchase` fully) -- the block is purely client-side routing, before the store is ever touched.

## Two-phase delivery (adversarial verification -> GO with 4 corrections -> implementation)
Full investigation was done in three passes: (1) initial root-cause analysis, (2) adversarial verification of the fix plan against every UserSubscription writer + deployment risk, (3) implementation. The adversarial pass caught a real correctness bug in the naive plan (see "promo must not downgrade purchase" below) and a real deploy-ordering risk (see "why split into two commits" below) -- both worth re-reading `project_high001_cross_account_receipt_guard_2026_08_16.md`-style investigations before trusting a first-draft plan on this table.

## The fix
New column `user_subscription.granted_via VARCHAR(20)` (nullable, String+constants pattern like `UploadSessionStatusEnum`, NOT a SQLAlchemy `Enum`) + `SubscriptionGrantedViaEnum` class in `app/models/models.py` (`SIGNUP_TRIAL`/`PROMO`/`PURCHASE`, lowercase values -- contract with Flutter, which checks for the literal string `'purchase'`). New additive `premium_source` field on `GET /get_user_profile_and_subscription` (`subscription_is_active` unchanged -- zero risk to feature-gating or old builds). Flutter follow-up (NOT done in this task, separate build): gate `PremiumView` on `subscriptionIsActive && (premiumSource=='purchase' || premiumSource==null)` instead of raw `subscriptionIsActive`.

## Why split into two separate commits (migration-only, then model+code)
`UserSubscription` is loaded as a FULL ORM entity (not a column-selected query) in `is_user_premium()` (`_therapy_helpers.py`) -- the premium gate hit on nearly every premium-gated request across the whole app -- plus `deactivate_expired_subscriptions`, `_activate_user_subscription`, `activate_user_access_until`, `prep_card_auto_generate.py`, `realization_detection.py`, `posthog_service.refresh_behavioral_properties`, `crud.get_users_with_active_subscription` (called from `mental_health_card.py`/`profile_service.py`). If the model change (adding the `Column(...)` to the class) deploys before the migration runs on Heroku, EVERY one of those full-entity SELECTs 500s on `UndefinedColumn` -- this is a much wider blast radius than the precedent migration `nn5o6p7q8r9s` (`platform_transaction_id` on `subscription_receipts`, read only by new dedicated code, safe to ship "migrate right after deploy"). Splitting the migration into its own commit means it can be deployed+migrated on Heroku at any time with zero code depending on the column yet, THEN the model/writer/endpoint commit ships whenever convenient, fully eliminating the deploy-order risk instead of racing it.

## Backfill precedence + the 4-day-shape refinement
Idempotent, 3 SQL passes in the migration (`purchase` > `promo` > `signup_trial`, else NULL): (1) `purchase` if a VERIFIED row exists in `subscription_receipts` for the user_id, (2) `promo` if a row exists in `user_promo_code`, (3) `signup_trial` -- **refined mid-task per operator instruction after live DB recon**: is_active AND no receipt/promo AND `end_date - start_date` is EXACTLY 4 days (the known signup-trial shape), checked in a **Python loop, not SQL** (interval arithmetic isn't portably expressible across Postgres/SQLite in one `text()` string; the row count here is tiny -- one-time backfill, not a hot path -- so a per-row loop is both simpler and safer than dialect branching). An active row with no receipt/promo whose span is NOT exactly 4 days (e.g. a real subscriber's period) is deliberately left NULL, not misclassified -- the client's safe default for NULL is unchanged (PremiumView), so this is a pure safety margin, confirmed to change nothing against current prod data (recon showed 8/8 real candidate rows already have the exact 4-day shape).

## Adversarial-verification-caught bug in the naive plan: promo must never downgrade purchase
Promo redemption (`POST /promo-code/verify`) mutates the SAME existing row in place and only actually changes anything when `prev_days < extend_days` (an early-return "no_extension_needed" path leaves the row completely untouched otherwise). The naive plan ("promo redemption always writes `granted_via='promo'`") would silently downgrade a real payer topping up extra days via a promo code back to 'promo' -- showing them the buy screen again despite an active paid subscription, and contaminating `paywall_shown` funnel metrics for someone already paying. Fixed with a guard: `if sub.granted_via != PURCHASE: sub.granted_via = PROMO` -- purchase always wins and is never downgraded by anything else. Covered by `test_promo_never_downgrades_an_existing_purchase` in `app/tests/test_granted_via_writers.py`.

## Writer #6 (PUT /subscription) residual risk, documented not fixed
`schemas.UserSubscriptionCreate` (the request body for `PUT /subscription`) has no `granted_via` field, so `crud.update_user_subscription`'s generic setattr loop structurally cannot touch it -- confirmed DEAD in the current Flutter client (grep of `lib/` finds only `POST /subscription` ever called, via `UsersManager.createUserSubscription`; zero PUT call sites). Left as-is with an explanatory comment rather than fixed, since it's unreachable from the shipped app and out of this task's scope.

## Gotcha: FastAPI response_model silently drops undeclared dict keys
Adding `"premium_source": granted_via` to the endpoint's returned dict is NOT sufficient on its own -- `schemas.UserProfileResponseWithTrial` (the `response_model`) must also declare `premium_source: Optional[str] = None`, or FastAPI filters the key out of the actual JSON response silently (no error, just missing data). Easy to miss since the endpoint code "looks correct" without it.

## Gotcha: real PostHog network calls hang pytest for 100s+ with no timeout plugin
Calling `users_ep.update_user_subscription()` (the actual FastAPI endpoint function) in a test triggers a real, unmocked `refresh_behavioral_properties()` -> `posthog_identify()` call (imported fresh inside the function body, so mocking `users_ep.posthog_capture` at module scope does NOT cover it) that hangs for 100+ seconds with no visible error (this repo has no `pytest-timeout` plugin installed). Fix: test the underlying writer directly (`crud.update_user_subscription`) instead of the full endpoint, when the endpoint's only side effect you don't want is an unrelated PostHog call you're not testing. `_capture_payment_event`-style calls ARE safe to leave unmocked in some paths since they're wrapped in try/except AND go through the already-patched `users_ep.posthog_capture` -- but `refresh_behavioral_properties` is a different function importing PostHog's `identify()` directly, not covered by that patch.

## PROD INCIDENT 2026-08-18: pass 3 of oo6p7q8r9s0t's backfill classified ZERO rows on prod
Migration `oo6p7q8r9s0t` was deployed and run on Heroku; passes 1-2 worked (35 `purchase`, 10 `promo`), but pass 3 (`signup_trial`, requires comparing `start_date`/`end_date` span to exactly 4 days) classified **zero** of the 8 rows that genuinely qualified. Root cause: `_coerce_datetime`'s `isinstance` checks only handled `datetime.datetime` and `str` -- **psycopg2 returns plain `datetime.date` objects (not `datetime.datetime`) for `user_subscription.start_date`/`end_date`** on this prod environment (schema drift from the `DateTime(timezone=True)` the SQLAlchemy model declares). Since `datetime.datetime` is a SUBCLASS of `datetime.date`, the `isinstance(value, datetime)` check does not match a real `date` object, so every row fell through to `return None`, silently skipped.

**Why the offline SQLite test suite (`test_migration_granted_via.py`, 15 tests, all green) completely missed this**: a raw `bind.execute(text(...))` query against SQLite only ever hands back whatever the sqlite3 DBAPI naturally returns for a column value -- for ISO-format strings inserted by the test harness (`datetime.isoformat()` then bound as a string param), that's always `str`, never a real `date`/`datetime` Python object. There is no way to make a raw-text SQLite query return actual `date` objects the way psycopg2 does for a genuinely `date`/`timestamptz`-typed Postgres column -- this failure mode was **structurally invisible** to any SQLite-only migration test, no matter how thorough. This is the exact same *class* of bug CLAUDE.md already names ("SQLite masks Postgres"), just manifesting in query-RESULT DATA TYPING this run, not DDL compilation. **Lesson for future migrations with any `bind.execute(text(...)).fetchall()` + Python-side row processing: any offline SQLite test of that code MUST separately unit-test the row-processing/coercion function with real `datetime.date`/`datetime.datetime` objects constructed directly in the test (not via a DB round-trip) -- a DB-round-trip-only test through SQLite cannot catch a psycopg2-vs-sqlite3 driver return-type mismatch, because SQLite structurally cannot reproduce psycopg2's return types for date/timestamp columns.**

**Fix**: added `isinstance(value, date)` branch to `_coerce_datetime`, positioned AFTER the `datetime` check (datetime is a subtype of date -- checking `date` first would misroute real `datetime` values and silently drop their time-of-day component). Applied to BOTH the original migration (`oo6p7q8r9s0t`, in-place edit -- so a fresh DB running the whole chain from scratch backfills correctly on the first pass) and a new corrective migration `pp7q8r9s0t1u` (down_revision=`oo6p7q8r9s0t`, re-runs all 3 passes idempotently with the fixed helper -- prod already ran the broken `oo6p7q8r9s0t` and Alembic never replays an already-applied revision, so only a NEW migration can repair prod's data). `pp7q8r9s0t1u`'s `downgrade()` is a deliberate no-op (documented in its docstring): it's a pure data correction with no schema change, and "reverting" it would just reintroduce the known bug.

Extracted the per-row decision into its own pure function `_signup_trial_span_matches(start_value, end_value)` (in both migration files) specifically so it's directly unit-testable with real `date`/`datetime` objects without needing a DB round-trip at all -- see `app/tests/test_migration_granted_via_date_coercion_fix.py` (22 tests: chain-tip for the new head, `_coerce_datetime`/`_signup_trial_span_matches` fed real `date` objects reproducing the exact prod bug, id=298's 730-day span confirmed to correctly stay `NULL` both before and after the fix, an explicit "old buggy helper vs fixed helper" characterization test, plus a light end-to-end SQLite idempotency check for the new migration).

Prod repair confirmed via read-only recon before writing the fix: 9 active `granted_via IS NULL` rows total -- 8 with an exact 4-day span (ids 31153, 31186, 31219, 31220, 31252, 31286, 31287, 31318, all genuine signup trials, all get fixed to `'signup_trial'` by `pp7q8r9s0t1u`) + id=298 with a 730-day span (2024-12-19→2026-12-19, no receipt/promo, a manual/ad-hoc grant) which correctly stays `NULL` -- the 4-day-shape guard itself was never broken, only the type coercion feeding it.
