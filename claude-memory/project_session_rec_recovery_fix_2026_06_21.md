**Root cause (double failure, both layers):**
- FE: splash recovery did `context.push(recordScreen)` then `context.go(main)` → `go()` destroyed the pushed screen + its RecordSessionCubit + the in-flight upload (D3). `_assembleAndUploadV2Session()` was an unfinished Phase-A STUB that silently `return`ed for `.pcm` segments (D4). No progress UI / no timeline refresh (D5). Recovery skipped when Firebase null on cold start (D1) and gated by live PostHog flag → orphaned manifest (D7).
- BE: `POST /upload/{id}/complete` did a SYNCHRONOUS AssemblyAI upload of the full assembled audio in the request thread → H12 (Heroku 30s, web is `--workers 1`) for big files → `session_recordings` row never created → nothing in timeline (the row IS the timeline entry; `_fetch_recordings_for_timeline` doesn't filter status). And there was NO server-side job to finalize a stuck UploadSession (only a 7-day ABORT cleanup) — so a killed client = lost recording.

**Fix BE (backend-api, no migration):** async `/complete` returns fast `201 {recording_id, processing_status}`, creates row immediately, enqueues Whisper/GCS worker job. NEW RQ job `finalize_complete_upload_sessions` (every ~15 min, in recording_recovery.py + registered rq_scheduler_setup.py + main.py lifespan) — server-side safety-net: finalizes UploadSessions with `bytes_received>=total_bytes` AND status in_progress AND recording_id IS NULL; idempotent via `.with_for_update()`; only fully-received (never truncates partial). `recover_stuck_recordings` GCS-first + NULL last_processing_attempt_at handled. `cleanup_abandoned_upload_sessions`/`get_abandoned_upload_sessions` now exclude `recording_id IS NOT NULL` (won't delete audio a recording needs). Logs redacted (no user_id↔storage_key).
