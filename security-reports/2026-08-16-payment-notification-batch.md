### Executive Summary

The receipt-verification reordering (verify-before-complete, with a bounded retry and a deliberately-left-pending transaction on failure) is a correct and well-reasoned fix. The backend's activation logic (`_activate_user_subscription`, `activate_user_access_until`) writes an **absolute** `end_date` derived from Apple/Google's own response on every call, so the new client-side retry cannot cause a double grant or a double charge — re-verifying the same receipt twice is idempotent by construction. Auth scoping is correct throughout (`current_user_id` always comes from a verified Firebase token via `deps.get_current_user`, never from the request body). The Firebase-analytics crash fix and the `error.toString()` → `error.runtimeType.toString()` change are genuine privacy improvements with no remaining path in the diff that sends raw exception text, therapy content, or tokens to Firebase. The backend notification-pipeline changes (moment_id FK, `push_delivered` reconciliation, `moment.expired` attribution, ADD_THERAPY_DATE throttling) touch no attacker-reachable endpoint, carry no therapy content in their PostHog properties, and do not weaken GDPR erasure or retention.

One **High** finding blocks part of this batch: accepting `PurchaseStatus.restored` in `SubscriptionRepository.markAsSubscribed`/`markAsOneTimePurchased` now routes restored receipts to `/subscription_data` / `/one_time_purchase`, and neither endpoint checks whether the underlying Apple/Google transaction (`order_id` / `purchase_token`) is already bound to a **different** `user_id`. This lets one paid purchase grant free premium to a second (or third, or Nth) account via the native "Restore Purchases" button — no jailbreak, no receipt theft required, just logging into a second MindSync account under the same Apple ID / Google account and tapping restore. This gap is pre-existing in the backend endpoint, but it was **not reachable via the legitimate restore flow before this diff** (the old client silently no-op'd on `.restored`), so this diff meaningfully widens its exploitable surface. The payment-ordering fix itself does not depend on this and is safe to ship independently.

### High Findings

#### HIGH-001: Restored receipts are not bound to the submitting account — one purchase can free-ride multiple Firebase accounts
- **Severity**: High
- **Location**:
  - `mindsync-frontend/mindsync_app/lib/providers/subscription/subscription_repository.dart:24-28, 54-58` (new `.restored` acceptance — the change that widens reachability)
  - `MindSync/app/api/v1/endpoints/users.py:430-550` (`POST /subscription_data`) and `:553-660` (`POST /one_time_purchase`) — **unchanged by this diff**, pre-existing gap
  - `MindSync/app/models/models.py:533-554` (`SubscriptionReceipt` — no unique/indexed constraint on `order_id` or `purchase_token`, and no cross-user lookup anywhere in `crud.py` or `users.py`)
- **Description**: `_verify_apple_receipt`/`_verify_google_receipt`/`verify_apple_one_time_product`/`verify_google_one_time_product` independently verify the submitted receipt against Apple/Google's real servers — that part is correct, the client's claimed `PurchaseStatus` is never trusted. But once verification succeeds, `_activate_user_subscription`/`activate_user_access_until` grant premium to **whichever `current_user_id` the request's Firebase token belongs to**, with no check that this exact transaction (`order_id` for Google, the transaction identified inside the Apple receipt) hasn't already been verified and activated for a *different* `user_id`. `SubscriptionReceipt.order_id`/`purchase_token` carry no unique constraint (global or per-user), and no query in `crud.py`/`users.py` looks up existing receipts by these fields before activating.

  Before this diff, `markAsSubscribed`/`markAsOneTimePurchased` only accepted `PurchaseStatus.purchased`, so tapping "Restore Purchases" was a silent no-op — the receipt never reached these endpoints via that path. This diff intentionally fixes that (restoring is a required App Store feature and was a real bug: restores never actually re-verified with the backend), but as a side effect it now also submits the receipt for verification+activation whenever a user restores. A completely ordinary, zero-skill sequence exploits this: buy premium once on Account A (device 1), log out, sign into Account B (device 2 or the same device, same Apple ID/Google account), tap "Restore Purchases" in the subscription screen. iOS/Android hand back the same underlying transaction with `status == restored`, the app now submits it, the backend verifies it against Apple/Google (genuinely valid — it *is* a real transaction), and activates Account B's `UserSubscription` for free. This can be repeated for any number of additional Firebase accounts from one paid purchase. It also happens *unintentionally* for ordinary family-Apple-ID households.
- **Impact**: Unbounded free-riding on a single real purchase — direct revenue leakage, and the most trivial version of the attack (create N accounts, purchase once, restore N times) requires no technical sophistication at all. This is a monetization/entitlement-integrity issue, not a mental-health-data exposure — no therapy content, PII, or credentials are exposed to the second account beyond premium access itself.
- **Reproduction steps**: Purchase `ms_premium_m_...` (or `ms_starter_package`) under Firebase Account A in a sandbox/TestFlight build. Sign out, create/sign into Firebase Account B on the same Apple ID / Google Play account. Open the subscription (or daily-page starter-package) screen and tap "Restore Purchases." Observe `POST /subscription_data` (or `/one_time_purchase`) fire under Account B's token, return `"status": "VERIFIED"`, and Account B's `UserSubscription.is_active` become `True` with the same `end_date` as Account A — with no second payment.
- **Remediation** (assign: **backend-api**): Before calling `_activate_user_subscription`/`activate_user_access_until`, look up existing `SubscriptionReceipt` rows with `status == "VERIFIED"` and the same `(platform, order_id)` (Google) or the same Apple original-transaction identifier (parse `original_transaction_id` out of `latest_receipt_info`/`in_app`, not just `order_id` which iOS requests don't even populate) for a **different** `user_id`. On a match, either (a) reject the new activation and emit a `subscription_verification_failed` event with a distinct `failure_reason` (e.g. `already_bound_to_other_account`) so growth-analyst can see volume, or (b) if family-sharing support is an intentional product decision, make that explicit and rate-limit/flag it instead of silently allowing unlimited re-activation. Add a unique index on `(platform, order_id)` for Google (order_id is Google's real dedup key) as a DB-level backstop once the app-level check exists; Apple's `original_transaction_id` should get the same treatment. This does not need to block the payment-ordering fix (see below) — it specifically gates the `.restored`-acceptance lines.

### Low Findings

- **LOW-001 — Recovery from a left-pending transaction is manual (reopen the subscription/starter-package screen), not automatic; this is a net improvement over current prod behavior, not a regression.** There is deliberately no app-lifetime `InAppPurchase.instance.purchaseStream` listener (confirmed — only `SubscriptionCubit` and `StarterPackageCubit` call `_setupPurchaseStream()`; no equivalent exists in `main.dart` or `service_locator.dart`). If backend verification keeps failing, the native transaction stays pending until the user revisits one of those two screens, which redelivers it. This was already true before this diff for a narrower failure window; the new ordering actually *closes* the worse pre-existing gap (old code completed the native transaction unconditionally before verifying, so a failure there permanently lost the ability to redeliver — "charged, never verified, no recovery path at all"). One asymmetry worth knowing: on **Android**, Google Play auto-refunds/revokes any purchase left unacknowledged for 3 days, so a prolonged backend outage self-heals there (no permanent charge without entitlement, just a lost sale); **iOS has no equivalent forced-refund**, so a user who never reopens either screen can stay in "charged, not entitled" indefinitely. Recommend flutter-mobile prioritize the already-flagged app-lifetime listener (or a call to `restorePurchases()`/purchase-stream drain on app launch) given this is a real-money flow — not a blocker for this batch.
- **LOW-002 — Duplicate `SubscriptionReceipt` rows accumulate on retry, with no dedup key.** Each `_verifyReceiptWithRetry` attempt inserts a fresh `SubscriptionReceipt` row (no upsert), so a network-drop-then-retry leaves 2 rows for what was one submission. Harmless to entitlement correctness (verified above) and to GDPR (all rows cascade-delete with the user), but worth a backlog note for `backend-api`/`database-administrator` if receipt-row volume or audit-trail clarity ever becomes a concern.
- **LOW-003 — Firebase `errorStack` is still sent as raw (though now length-capped) text.** `AnalyticsEvents.logError` fixed the dangerous half (`errorMessage` is now `error.runtimeType.toString()`, never the free-text message that could embed therapy content) but `errorStack: stackTrace?.toString() ?? 'No stack trace'` still passes the real stack trace into `_sendToFirebase`, which truncates it to 100 chars via `_sanitizeParameters` but does not redact it. Dart stack traces are code paths/line numbers, not user content, so this is low risk — flagging only because "truncated" is not "safe by construction": `_sanitizeParameters` protects against malformed calls and oversized values in general, not specifically against a future call site that passes user-generated text as a parameter value. No such call site exists in this diff or in the 3 real `logError` call sites found (`error_view.dart`, `dio_client.dart`, `auth_service.dart`) — this is a defense-in-depth note for future changes, not a finding against this diff.

### Verdict

**Conditional GO — split the batch.**

- **Ship now, unblocked**: the verify-before-complete payment ordering (the retry + leave-pending-on-failure logic in `subscription_cubit.dart`/`starter_package_cubit.dart`), the `subscription_verification_failed` analytics event, the Firebase-analytics crash/privacy fix (`analytics_events.dart`), the `subscription_screen_opened`/deep-link attribution change (`ms_routes.dart`), and the entire backend notification-pipeline batch (`moment_id` FK/migration, `push_delivered` reconciliation, `moment.expired` attribution, ADD_THERAPY_DATE throttling + copy fix). None of these have Critical or High findings; the migration is idempotent, additive, dialect-safe, and does not weaken GDPR erasure or retention.
- **BLOCKED**: the two-line change in `subscription_repository.dart` that makes `markAsSubscribed`/`markAsOneTimePurchased` accept `PurchaseStatus.restored` (HIGH-001), until `backend-api` adds a cross-user receipt-binding check on `/subscription_data` and `/one_time_purchase`. Per CLAUDE.md, a High finding blocks deployment of the piece it's attached to; the rest of this batch is not implicated and does not need to wait on it.

If the team wants to ship `.restored` support today anyway (it does fix a real, already-shipped bug where restores silently never reached the backend), the minimum acceptable mitigation before deploy is the reject-on-cross-user-match check described in HIGH-001's remediation — it is a small, self-contained change (one lookup query before `_activate_user_subscription`/`activate_user_access_until`) and does not require touching the receipt-verification calls themselves.
